# 统一文件索引（2026-10-24）

基于现有全局 / 单邮箱文件页 `8954900`，将两个文件接口接到同一个持久化元数据索引。本文件记录实现与发布前验证结果。

## 查询与页面

- 保留 `/files`、`/mailbox/:mailboxId/files` 及两个现有 HTTP API。文件查询只访问 `FileIndexDO`，不再遍历所有邮箱、逐个读取附件并合并分页。
- 保留全部 / 收到 / 发出、精确邮箱、正文图片开关、文件预览、下载和来源邮件入口。邮箱存在性仍由 R2 `head` 检查，下载仍校验邮箱、邮件、附件的归属。全局页面的邮箱下拉列表另行加载目录，不阻塞文件查询。
- SQLite 索引存储附件属性及 `mailboxId`、`email_id`、`folder_id`、`thread_id`、邮件主题、收发地址、时间和原始收发方向；不复制邮件正文或文件内容。
- 普通列表使用按时间排序的复合索引，并针对邮箱、收发方向、排除内嵌图片分别优化。相同日期按邮箱、邮件、附件标识倒序稳定排列。
- 搜索文件名、邮件主题、收发地址和所属邮箱；至少 3 个 Unicode 字符的查询使用 FTS5 trigram，再校验字面子串。大小写统一处理，百分号、引号等字符不作为查询操作符。1–2 个字符仍支持，但需要扫描筛选后的元数据。
- 新增 `cursor` 参数与 `nextCursor` 响应，常规前后翻页用复合键定位。游标绑定邮箱和搜索条件，错误或跨条件复用返回 400。旧数字页码链接仍兼容，未带游标的深页使用 OFFSET。
- 输入搜索防抖 300 ms；前端缓存 15 秒并预取下一页，取消过期请求。后台补录时每 2 秒更新列表，完成后每 15 秒刷新。条件和游标保留在 URL 中。
- 点击来源邮件后展开所选邮件，避免同一会话中自动展开其他邮件。

## 后台同步与恢复

```mermaid
flowchart LR
    M["邮箱邮件与附件"] --> T["事务内触发器"]
    T --> O["持久化变更队列"]
    O --> A["MailboxDO alarm"]
    A --> I["统一 FileIndexDO"]
    I --> G["全局文件页"]
    I --> S["单邮箱文件页"]
    R["R2 邮箱目录"] --> D["后台分批发现"]
    D --> A
```

- 邮箱迁移 `11_file_index_outbox` 添加附件所属邮件索引、同步状态和变更队列。附件增删改、邮件主题 / 地址 / 日期 / 文件夹 / 会话 / 收发方向变化，以及级联删除，都通过 SQLite 触发器与原始变更一起持久化。
- 首次查询启动后台目录发现：每批最多 100 个邮箱，每轮最多并发提醒 5 个邮箱。目录游标、待办及失败次数持久化，不受单次请求或进程生命周期限制。
- 单邮箱请求优先排入补录任务。历史附件按邮件 ID 游标分批读取，每批最多 25 封邮件，仅读取附件与邮件元数据。新到附件由变更队列接续，不依赖历史扫描位置。
- 正常增量安排约 1 秒后的 alarm；持续收信不会把同一个 alarm 一直推迟。重启时重新安排未完成或已过期的同步任务。
- 同步先在索引事务内落库，再确认并清理源队列。每封邮件的 revision 去重、拒绝旧数据；删除记录也保留版本标记。重复投递、确认丢失、同步期间新修改都可收敛。
- 邮箱删除提升 generation，并在删除接口返回前移除索引；延迟批次无法复活旧数据。显式重建邮箱提升 generation 并重新补录。后台发现不会重新启用已删除邮箱。
- 协调器保留发现任务直到源邮箱报告补录完成，每 30 秒提醒未完成任务。发现失败采用指数退避，最高 5 分钟；源同步也保留重试 alarm。
- 首次补录可分批显示结果，响应 `index.state=building` 和进度；页面显示“已找到”和整理提示。完成后显示 `ready` 及完整数量。新变更采用最终一致性，显示时间受 alarm、批次积压与前端刷新间隔影响。
- 本地导入专用 Worker 可不配置 `FILE_INDEX`，变更队列仍持久化，待绑定可用后处理。正式绑定故障返回 503，不退回请求内遍历全部邮箱。

## 可复现性能数据

执行：

```sh
node --experimental-strip-types scripts/benchmark-file-index.mjs 100000
```

本地 Node SQLite 内存库，10 万条合成附件、200 个邮箱；使用生产查询实现，含总数统计与状态读取。每项预热 5 次、采样 50 次。数据装载耗时约 8.26 秒。

| 查询 | 中位数 | P95 |
| --- | ---: | ---: |
| 全局首屏 50 条 | 0.774 ms | 0.848 ms |
| 单邮箱首屏 50 条 | 0.124 ms | 0.146 ms |
| 收到的文件首屏 | 1.240 ms | 1.459 ms |
| 中文较长关键词 | 0.125 ms | 0.130 ms |
| 两字关键词无结果 | 45.627 ms | 49.133 ms |
| 接近末尾的游标页 | 0.778 ms | 0.864 ms |

上述为本地数据库测量，不含 Cloudflare 网络、RPC、冷启动和实际数据分布，不能视作线上端到端延迟。短关键词和常见关键词的大结果集仍受扫描 / 计数成本影响。

## 验证与部署准备

- `npm test` 共 70 项通过。自动化覆盖 1,003 个邮箱的后台发现、读取路径不扇出、历史补录、同时间分页、插入与删除期间翻页、Unicode / 标点搜索、收发与内嵌筛选、邮件映射、过时批次、重试、重启恢复、事务回滚、删除失败后的恢复和删除后的重建。
- `tests/file-index-runtime.test.mjs` 在真实本地 workerd 中运行 SQLite Durable Objects 和 R2，验证 alarm 自动补录、实际 FTS 支持、HTTP 参数校验、附件字节与归属、移动和删除后的收敛。
- 浏览器以本地合成数据验证全局 33 条文件、两页游标、输入搜索自动重置分页、全局精确邮箱筛选、单邮箱正文图片开关和打开正确来源邮件。截图保存在 Coda uploads 的 `file-index-20261024/`。未修改生产邮箱或发送外部邮件。
- `npm run typecheck`、`npm run build`、`npx wrangler deploy --dry-run` 通过；构建仍有既有的大资源块提示。
- Wrangler 新增 `FILE_INDEX` 绑定、`FileIndexDO` 导出及 `v4` SQLite Durable Object 迁移，索引实例名称固定为 `files-v1`。发布后的首次文件查询会自动启动历史补录，无需人工导出或搬运附件内容。
- 原始邮件与附件继续作为数据源；此次不提供人工清空 / 全量重建索引接口。

实现依据：[Cloudflare SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)、[SQLite FTS5 trigram tokenizer](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。
